# 0004. 视口感知优先级调度与单探针风控熔断恢复

## 决策背景与核心决定

每个主播 Profile 的 SSR 页面体积约 289 KB，列表滚动可能短时间内触达数十个主播。若盲目全量抓取或爆发式并发，将消耗巨量带宽并瞬间触发小红书反爬验证码或 HTTP 429 限制；若在风控暂停后盲目重试，更会导致账号惩罚。

我们决定采取极限安全与视口驱动的调度体系：
1. **视口驱动调度**：结合 `MutationObserver` 发现节点与 `IntersectionObserver`（带 200px buffer）感知可见性，确保当前视口可见卡片永远最高优先级；当用户快速滑过时，直接从待处理队列丢弃已脱离视口的卡片（Stale Drop），但允许已在途的请求（In-flight）正常完成并落库。
2. **两级缓存保障**：使用内存 `Map`（一级）与 Tampermonkey `GM_getValue`/`GM_setValue`（二级持久化）双层缓存，设置 24 小时 TTL 与约 2000 条的容量上限（超限按 `fetchedAt` 淘汰最旧条目），同一会话对同一主播 0 重复请求。
3. **风控熔断与单探针恢复**：遭遇 429、验证码重定向或异常时，立即将调度器置为 `PAUSED` 态并停止发起新抓取，UI 显示“已暂停 · 风控保护”；用户手动点击 `[恢复]` 时，调度器**仅执行单一试探性探针（Single Probe Request）**，探针成功方切回 `RUNNING` 释放积压，探针失败则维持 `PAUSED`，严禁并发冲击或自动死循环重试。

## 权衡与考量 (Trade-offs)

彻底将“反爬安全性与系统稳定性”置于“首屏吞吐速度”之上，宁可丢弃已划离屏幕的预加载任务、宁可在风控后依赖单探针试探，也绝不引发平台级反爬惩罚。
